## Critical

### C1. ตารางที่ใช้ร่วมกัน (shared) ไม่ได้เปิด RLS — anon key เขียน/ลบได้
`supabase/migrations/20260919000000_foundation.sql:321-326` เปิด RLS เฉพาะ 6 ตาราง user
ส่วน `vocabulary`, `vocabulary_readings`, `vocabulary_examples`, `vocabulary_relations`, `media_assets`,
`vocabulary_enrichment`, `import_batches`, `decks`, `source_notes_raw`, `source_cards`, `source_revlog`,
`source_models`, `source_field_mappings` **ไม่มี RLS และไม่มี policy**
Supabase เปิด `public` schema ผ่าน PostgREST ดังนั้นใครที่มี anon key (ซึ่งอยู่ใน bundle ของ browser by design, ADR-009)
สามารถ `INSERT/UPDATE/DELETE` คำศัพท์กลาง, อ่าน raw Anki dump และ revlog ได้
ต้องแก้ก่อน deploy หรือเก็บข้อมูลจริงเข้าไปอีก:
เปิด RLS ทุกตาราง + policy `select` สาธารณะเฉพาะตารางเนื้อหา, ปิดตาราง `source_*`/`import_*` ไม่ให้ anon/authenticated เห็น,
เขียนได้เฉพาะ service role

### C2. ข้อมูลความคืบหน้าที่ผู้ใช้เห็นเป็นข้อมูลปลอม
`src/lib/srs.ts:105-142,148` — `makeSeed()` สร้างการ์ด 214+ ใบ, log รีวิวหลายร้อยรายการ, streak 12 วัน
เป็น state เริ่มต้นของ **ทุกคน** (ไม่ใช่เฉพาะ dev) หน้า Today/Progress จึงแสดง "learned", "streak", retention
ที่ไม่เคยเกิดขึ้นจริง และปุ่ม "Reset demo data" ก็ reset กลับไปเป็นข้อมูลปลอมชุดเดิม (ไม่ใช่ศูนย์)
ผู้ใช้ใหม่เริ่มโดยมีคำ 214 คำ "เรียนไปแล้ว" ทำให้ new-card queue ข้ามไป 214 คำแรกของเด็ค

## High

### H1. สอง source of truth + map ID ด้วยตัวอักษรคำศัพท์
เนื้อหาในแอปมาจาก `src/data/kaishi.json` (id 1..1500 + extras 1501-1506 ใน `vocab.ts`)
แต่ Supabase มี `vocabulary.id` เป็น uuid คนละชุด `library.ts` จับคู่ด้วย `.eq("word", word.word).limit(1)`
(`library.ts:33-44`) ทั้งที่ ADR-007 บอกชัดว่า word ซ้ำกัน (24 คำ) → My Words/โน้ตของคำซ้ำชี้ไปแถวผิด
เมื่ออ่านกลับ (`library.ts:114-118`) ใช้ `Array.from({length:1500},(_, i)=>i).find(...)` ซึ่งเริ่มที่ 0
→ id 1500 ไม่มีทางถูกพบ, extras (1501+) ซิงก์กลับไม่ได้, และเป็น O(n) ต่อแถว
สำหรับ `extras` ไม่มีแถวใน DB เลย (`lookup` คืน null เงียบๆ → ไม่ซิงก์)

### H2. การซิงก์ My Words ทำให้ข้อมูล local หาย
`hydrateRemoteLibrary` (`library.ts:60-87`): ถ้าผู้ใช้ล็อกอินแล้ว remote ว่าง จะ `state = {}` + `persist()` ทันที
→ คำที่บันทึกตอนเป็น guest ถูกลบทิ้งโดยไม่เคยอัปโหลด (data loss ตอนล็อกอินครั้งแรก)
ไม่มีการ merge, ไม่ได้ subscribe `onAuthStateChange` (ล็อกอินหลังโหลดหน้าแล้วไม่ซิงก์จนกว่าจะรีเฟรช),
ไม่ได้ล้าง state ตอน sign out (คนถัดไปบนเครื่องเดียวกันเห็นคำของคนก่อนหน้า)
ข้อผิดพลาดจาก Supabase ถูกกลืนด้วย `console.error` ผู้ใช้ไม่รู้ว่าซิงก์ล้มเหลว
และข้อความใน UI "synced when you sign in" (`vocab.$id.tsx`) ยังไม่จริง

### H3. คิว Review ถูกสร้างจาก state ก่อน hydrate
`review.tsx:42-48` สร้างคิวด้วย `useMemo(..., [])` ตอน render แรก ซึ่ง `useSrs()` ยังได้ seed (ข้อมูลปลอม) เพราะ `hydrate()` รันใน `useEffect` หลังจากนั้น
เมื่อเปิด `/review` ตรงๆ/รีเฟรช คิวจะมาจากข้อมูลปลอมเสมอ ไม่ใช่ความคืบหน้าที่บันทึกไว้
นอกจากนี้ `Math.random()` ใน `useMemo` ทำให้ SSR กับ client ได้ค่าต่างกัน (hydration mismatch)

### H4. Contrast card ไม่ทำให้ SRS เดินหน้า และปนกับ recall
`recordContrast` (`srs.ts:164-172`) เมื่อตอบถูกไม่เปลี่ยนอะไรกับการ์ด (ไม่เพิ่ม `reps`, ไม่ย้าย `due`) และ step นี้ไม่เรียก `rate()`
→ การ์ดที่ถึงกำหนดแล้วถูกสุ่มเป็น contrast ไม่ถูกจัดตารางใหม่ ยังค้างเป็น due ทุกครั้ง
→ การ์ด **new** ที่ถูกสุ่มเป็น contrast ไม่เคยกลายเป็นการ์ดที่เรียนแล้ว (`reps` ยัง 0)
ตอบผิดจะลด stability/เพิ่ม difficulty ของการ์ด recall ซึ่งขัดกับ spec §17 ที่ต้องแยก Recall ออกจาก Discrimination
(schema มี `user_fsrs_state.dimension` แล้ว แต่โค้ดมีแค่มิติเดียว)

### H5. ไม่ใช่ FSRS (ขัด ADR-003)
`srs.ts` เป็นสูตรที่เขียนเอง (`nextMemory`) ทั้งที่ ADR-003 และ workflow ห้าม ไม่มี `ts-fsrs` ใน `package.json`
`retrievability` ใช้สูตรไม่ตรง FSRS, ไม่มี learning steps จริง (Again = 10 นาทีตายตัว), `DESIRED_RETENTION` ไม่ถูกใช้คำนวณช่วงเวลา
(ใช้แค่แสดงผลในหน้า Progress) หน้า Progress เรียกว่า "FSRS-style forecast" จึงเข้าใจผิดได้

### H6. SRS/Review ทำงานแบบ guest + localStorage ขัด spec §4.4
spec กำหนดว่า SRS ที่บันทึกได้ต้อง login และ `review_history` / `user_fsrs_state` ต้องอยู่ใน DB
ปัจจุบันไม่มีการเขียนอะไรลง `user_fsrs_state`, `user_vocabulary_state`, `review_history`, `user_settings` เลย (grep แล้วไม่พบการใช้งาน)
ความคืบหน้าอยู่ใน `localStorage` ที่ key เดียวต่อเบราว์เซอร์ ไม่ผูกบัญชี ไม่มี migration ของ schema (`...-v1`)

### H7. ไม่มี test และ type check ไม่ผ่าน
- `npx tsc --noEmit` ล้มเหลว 2 จุด: `src/lib/supabase.ts:3-4` (TS4111, ต้องใช้ `import.meta.env["VITE_..."]`)
  `npm run build` ผ่านเพราะ Vite ไม่ type-check — commit "Fixed strict type errors" จึงยังไม่ครบ
- ไม่มี test framework หรือไฟล์ test เลย (Task 16 ยังไม่เริ่ม) ตรรกะ SRS, queue, library sync ไม่มีอะไรป้องกัน regression
- `eslint src` : 212 errors (ส่วนใหญ่ Prettier/CRLF) บวก `no-useless-escape` จริง 1 จุดที่ `vocab.ts:130`
  ไม่มี `.gitattributes`/`.editorconfig` ให้ line ending คงที่ ทำให้ lint ใช้เป็น gate ไม่ได้

## Medium

- **M1. ข้อมูล "confusable" กว้างเกินไป**: จาก 1,500 คำ มี 1,173 คำ (78%) ที่ `confusablesOf` ไม่เป็น null —
  701 คำเป็นแค่ "shared kanji" (ใช้ kanji ตัวเดียวกัน ไม่ได้แปลว่าสับสนกัน), 356 คำ "similar meaning", 116 คำ homophone จริง
  ตัวกรอง "Confusable only", ตัวเลข "Contrast groups" และ "flagged as confusing" จึงไม่มีความหมาย และคำนิยามคิดจาก
  heuristic ไม่ใช่ข้อมูลสับสนจริงของผู้ใช้ (spec §23 ต้องการจาก learning state + review history)
- **M2. หน้า Review แสดงปุ่มฟังเสียงก่อนเฉลย** (`review.tsx` การ์ด recall: `AudioButton text={word.word}` ก่อน `revealed`)
  speech synthesis อ่านคำให้ฟัง = เฉลยการอ่านก่อนตอบ ขัด ADR-004/spec §16.1 ส่วน contrast card แสดง `reading:` ในโจทย์ด้วย
  ยังไม่มี setting autoplay/ซ่อน reading (`user_settings` ไม่ถูกใช้)
- **M3. ชนิดการ์ดมีแค่ recall + contrast แบบเลือก 3 ข้อ** — spec §22 กำหนด Recall/Reading/Meaning/Contrast/Context
  คำตอบ contrast ใช้ `shuffle` แบบ deterministic ตาม id (`review.tsx`) ตำแหน่งคำตอบถูกจำได้ และถ้ามีตัวสับสนน้อยกว่า 2 จะเหลือ 2 ตัวเลือก
- **M4. ตัวนับ "Today" นับซ้ำ**: `total = due + new + done` แต่การ์ดที่เพิ่งกด Again ยัง due (10 นาที) และอยู่ใน `done` ด้วย
  `dueCards` มีเงื่อนไขแปลก `due <= now + 20h && due < todayStart+1d` (magic number) และ `newCards` นับวันใหม่จาก `reps === 1`
  ซึ่งพังเมื่อการ์ดถูกรีวิวซ้ำในวันเดียวกัน (ทำให้โควตา new/day คลาดเคลื่อน) หน้าเวลาประมาณ "≈ N min" คูณ 0.35 แบบ hard-code
- **M5. SSR/hydration**: `serverSnapshot = state` ถูกสร้างตอนโหลดโมดูลด้วย `Date.now()` ฝั่ง server; หน้าที่ใช้ `Date.now()`/`new Date()` ใน render
  (Today, Progress, detail) อาจ mismatch ระหว่าง server กับ client
- **M6. ไม่มีสื่อจริงจาก APKG**: `kaishi.json` ไม่มี audio และ image (มีแค่ `imageAlt`) มีรูป 3 ใบเฉพาะ extras ที่ import ตรงๆ จาก assets
  เสียง = `speechSynthesis` ของเบราว์เซอร์ (คุณภาพ/pitch accent ไม่ตรงเสียงเจ้าของภาษาในเด็ค) ทั้งที่ APKG มีเสียง 2,972 ไฟล์ รูป 1,382 ไฟล์
  ส่วน `extras` 1501-1506 เป็นข้อมูลที่เขียนมือ (โน้ต pitch เขียนเอง ไม่ผ่าน pipeline/ไม่มี provenance) ปนเข้า "Kaishi 1.5k" และตัวเลข "of 1506 words"
- **M7. ค้นหา**: ตัดผลที่ 120 รายการ ไม่มี pagination; ค้น romaji ไม่ได้; ไม่ได้ใช้ search index ที่ migration สร้างไว้ (`vocabulary_search_idx`)
  `user_vocabulary` ใช้ soft delete (`is_active=false`) แต่ยังไม่มีการกำหนด semantic ว่าเมื่อลบแล้วบันทึกซ้ำ โน้ต/สถานะ SRS ควรกลับมาหรือเริ่มใหม่
- **M8. เอกสารไม่ตรงกับโค้ด**: `docs/spec.md` ว่างเปล่า (0 บรรทัด) ทั้งที่ workflow อ้างถึง; `progress.md` ยังบอกว่า Task 6 เป็น localStorage ล้วน และ "Next Task = Task 1 validation"
  แต่ commit ล่าสุดทำ Supabase sync แล้ว; `implementation-plan.md` ยังไม่อัปเดต; `Backend_Specification_Updated.md` (1,858 บรรทัด) ใหญ่เกินกว่าจะใช้เป็น contract ที่ตรวจสอบได้ และผสม requirement กับ UI mockup
